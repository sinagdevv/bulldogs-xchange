# Operator account provisioning

This workflow remains disabled unless `ENABLE_OPERATOR_PROVISIONING=true`. Supply exactly four operator-approved records in a local JSON file. Each record has a real NU Fairview `email`; the workflow uses Supabase Admin Invite and never supplies a password, an alias, or `email_confirm`.

Run `npm run auth:provision-accounts -- --operator-provisioning=true --accounts-file=<path> --confirm="INVITE FOUR PENDING BULLDOGS XCHANGE ACCOUNTS"` for the default dry-run. Add `--dry-run=false` only after the project/database identity and dry-run results are approved. Every identity is created as Customer/pending; use the existing approval and exact-confirmation Admin bootstrap workflows afterward. The desired Admin, Staff, Faculty, and Customer assignments are applied only through their existing authorized role-management procedures.

Before activation, keep Supabase public signup disabled; use `{{ .ConfirmationURL }}` in invite/confirmation templates and `{{ .Token }}` in the email OTP template. Set the approved Auth OTP expiry and resend cooldown in Supabase; the API also applies its shared auth rate limit.

After an approved live invite, the recipient opens the Supabase invite confirmation link, then uses the configured eight-digit email code at the app. Do not approve or promote a recipient until the inbox owner has accepted the invite. Rollback a created entry in reverse order: identify its immutable `AuthSubject` and application `UserId` in a trusted operator session; verify it has no dependent business records; delete the Supabase Auth identity; then transactionally delete its pending approval/audit records and Customer row. Never delete an account with reservations, payments, inventory actions, or role changes. If provider creation succeeds but the database transaction fails, the CLI deletes that new Auth identity automatically.
